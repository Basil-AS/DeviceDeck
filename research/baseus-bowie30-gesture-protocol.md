# Baseus Bowie 30 legacy gesture protocol

## Evidence scope

Static analysis of the locally supplied Baseus Intelligent APK 2.18.0. This describes the commands generated by that application; it does not claim a hardware-verified DeviceDeck round trip. The local APK and its decompilation are not included in the public repository.

## Model profile

The bundled `gesture_config_layout.json` groups `Bowie 30` with `Bowie 35` and lists layout IDs in this order: `00`, `02`, `01` (double press, long press, triple press). Its defaults are double-click `01/01`, long-press `06/06`, and triple-click `04` for both sides. The model's `gesture_config_function_list.json` allows action IDs `[01, 03, 02, 04, 06, 00]`: play/pause, next, previous, voice assistant, cycle noise modes, and no action. The ordered list is the vendor UI's available-choice list, not an instruction to rewrite all defaults.

## Commands and response layout

`GestureBleManager.m31764d` constructs a query as `BA21` plus the two-digit layout ID. `m31766f` constructs the write as `BA22` plus a layout and two action IDs. The activity's v1 setter (`GestureSettingViewModel.m38385Z`) confirms the write result through `AA22` handling and schedules a subsequent gesture query.

`GestureSettingViewModel.m38376K` parses `AA21` as three bytes after the command: layout, left action, right action. The matching-model predicate treats Bowie 30 as a two-side profile. The expected byte shapes are therefore:

| Operation | Wire bytes | Expected response |
|---|---|---|
| Read double press | `BA 21 00` | `AA 21 00 <left> <right>` |
| Read long press | `BA 21 02` | `AA 21 02 <left> <right>` |
| Read triple press | `BA 21 01` | `AA 21 01 <left> <right>` |
| Change one side | `BA 22 <layout> <left> <right>` | `AA 22 01` success; then query `BA21` and compare the returned pair |

The unmodified side must be preserved in `BA22`. DeviceDeck should not send IDs outside the Bowie 30 resource list. Function 6 appears as the noise-cycle action, but the available static resource does not prove that Bowie 30 accepts child-mode editing; do not expose EP10 Pro's BA8E/BA8F child editor for this model.

## Transport

`BluetoothDataWriteManager` sends this model through the BLE SDK path, not the Classic Bluetooth/SPP path used for EP10 Pro and Bowie MF1. The helper accepts the model name and sends the command bytes to the connected device; the regional BLE dictionary supplies the GATT UUID profile. DeviceDeck uses its existing BLE session and shared accessory UI.

## Verification still required

Record an actual Bowie 30 exchange for each layout, then change one assignment on each side. Capture the request, `AA22` result, `AA21` readback, exact hardware and firmware, and reconnect persistence. Until then, label this feature implemented from static source and hardware-unverified.
