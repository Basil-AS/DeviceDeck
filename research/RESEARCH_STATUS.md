# Research status (2026-11-08)

## Completed

- Edifier Connect / ConneX static analysis from the supplied builds is archived in `edifier/EDIFIER_ANDROID_REVERSE_ENGINEERING.md` and `edifier/edifier_command_index.csv`.
- Supplied Baseus Intelligent 2.18.0 and realme Link 5.8.811.2814 split bundles were unpacked locally; their full bundle SHA-256 hashes are recorded in `APK_MANIFESTS.md`.
- Jadx produced local resource/source trees for the base APKs and reported recoverable errors (522 Baseus, 226 realme) after processing nearly all classes. Treat decompiled output as incomplete until key code paths are checked.
- Baseus Intelligent contains explicit profile/config entries for `Baseus Bass EP10 Pro`, `Bowie 30`, `Baseus Bowie MF1`, and `Blade 2`; examples appear in `DeviceResVersion1.java`, `DeviceManager.java`, and bundled gesture resource JSON. This proves model-specific app data exists, not that every advertised feature works over BLE.
- A focused Baseus report records model strings, resource categories, gesture function IDs, noise-mode UI evidence, and the current protocol boundary in [`baseus-intelligent-findings.md`](baseus-intelligent-findings.md). Partial DeviceDeck integrations now cover all four requested Baseus models across Android, Windows/Linux and macOS; controls remain unverified on physical hardware and gesture/port operations are still incomplete.
- Expanded Baseus static inventory now documents the Blade 2-140 mobile-power UI and app-layer BLE command/readout map: screen themes and custom text, timers, two Type-C ports' V/A/W/protocol, six-cell telemetry, temperatures, cycle count, status/error and module versions. See the Blade 2 section in [`baseus-intelligent-findings.md`](baseus-intelligent-findings.md). Command generation is verified in app code; device acceptance/scale/UUIDs are not hardware-verified.
- [`baseus-device-families.csv`](baseus-device-families.csv) inventories all 30 top-level app modules. It separates product families from services/infrastructure and explicitly marks family directories as presence evidence, not a complete current device catalog. The model CSV remains an earbud registry plus selected resource profiles.
- Additional static tracing now documents Baseus's shared `BluetoothDataWriteManager` paths, `BAxx` to `789C` framing/CRC conversion, response parser, BLE/classic transport branch, and dynamically downloaded per-model resources. These mechanics are not a target-model command map; the report lists exactly what remains unknown.
- The live Baseus `/app/devicebind/getProductResource` endpoint returned records for all four requested models. Downloaded profile ZIPs contain presentation assets/tutorials only; `gestureUrl` is null and there is no command table. The response, ZIPs, hashes, and manifest stay under ignored `local-evidence/baseus-resources/`. This closes the “what is in the product ZIP?” question but not device command discovery.
- A read-only request to Baseus's EU `/app/homepage/dictByName?dictName=app_device_ble_config` endpoint returned five UUID/config groups with 149 BLE model entries. [`baseus-ble-config-catalog.csv`](baseus-ble-config-catalog.csv) records the dated derived snapshot; Blade 2-140, Blade 2, Bowie 30, Bowie MF1, and EP10 Pro all appear in group 4 with the same service/write/notify UUID triple as the Baseus BLE audio profile. UUID discovery is now established; model identity, connect behavior and device-level command/readback still need validation.
- Targeted searches of the realme Link base APK source/resource output have not yet located the Air 7 / Air 7 Pro model names. Catalogs may be delivered through splits, native/assets data, or remote services; absence in this search is not proof of absent support.

2. Continue catalog analysis for Baseus non-BLE and cloud-controlled product families; this BLE dictionary is not the full Baseus app catalog. Keep dated regional snapshots and do not publish credentials, tokens, or user identifiers.
